## PassVault（ネイティブ版・凍結）

自分専用のパスワード管理アプリ。SwiftUI 製で macOS と iOS で同じコードが動く。
1Password に寄せた 3 カラム構成（カテゴリ → 一覧 → 詳細）。

## 使い方

```bash
open PassVault.xcodeproj
```

Xcode で ▶︎ を押せば起動する。ターミナルからビルドするなら:

```bash
xcodebuild -project PassVault.xcodeproj -scheme PassVault -destination 'platform=macOS' -configuration Debug -derivedDataPath build build && open build/Build/Products/Debug/PassVault.app
```

コアの検証（アプリを起動せず、暗号・TOTP・Watchtower の正しさだけを確かめる）:

```bash
./Tests/run.sh
```

## できること

| | |
|---|---|
| **アイテム種別** | ログイン / セキュアメモ / クレジットカード / ID・個人情報 / APIキー / Wi-Fi / ライセンス。種別ごとに入力欄が変わる |
| **ワンタイムパスワード** | RFC 6238 の TOTP。`otpauth://` の URI か Base32 のキーを貼れば、6 桁コードと残り秒数の輪を表示 |
| **Watchtower** | 使い回し・推測されやすい・長く変えていない・http:// のサイトを検出。通信は一切せず端末内で完結 |
| **パスワード生成** | 長さ・文字種を指定。紛らわしい文字（0 O 1 l I）の除外、エントロピー表示つき |
| **整理** | お気に入り、タグ、カテゴリ別の絞り込み、全文検索 |
| **パスワード履歴** | 変更すると古いものを 20 件まで保持 |
| **ゴミ箱** | 削除は一旦ゴミ箱へ。元に戻せる |
| **カスタム欄** | 項目ごとに好きな欄を追加できる |
| **同期** | 同じ Wi-Fi 上の 2 台を直接つないで突き合わせる。クラウドを介さない |

## 仕組み

保管庫は暗号化された 1 ファイル。中身は `~/Library/Application Support/PassVault/vault.pvlt`。

```
┌─ 平文ヘッダ (44 バイト) ────────────┬─ AES-256-GCM ────────────┐
│ "PVLT" │ version │ kdf │ 反復回数 │ salt │ nonce │ 暗号文 │ 認証タグ │
└────────────────────────────────────┴──────────────────────────┘
        └── これ全体を GCM の追加認証データにする ──┘
```

- **鍵導出**: PBKDF2-HMAC-SHA512、400,000 回、32 バイトの salt。マスターパスワードはどこにも保存しない。導出には意図的に約 0.4 秒かける（総当たり攻撃を遅くするため）
- **暗号化**: AES-256-GCM。認証つきなので、1 ビットでも書き換わっていれば復号が失敗する
- **ヘッダ改ざん対策**: 反復回数と salt を追加認証データに含めてある。これがないと「反復回数を 1 に書き換えて総当たりを楽にする」ダウングレード攻撃が通ってしまう
- **パラメータはファイルに記録**: 将来 400,000 回を増やしても、古い保管庫はそのまま開ける
- **生体認証**: マスターパスワードではなく導出済みの鍵をキーチェーンに預ける。`.biometryCurrentSet` 指定なので、指紋や顔を追加・変更すると OS 側で自動的に無効化される
- **クリップボード**: パスワードは 30 秒で自動消去。クリップボード履歴アプリ向けに「保存するな」の印も付ける
- **自動ロック**: 無操作 5 分（変更可）。iOS ではアプリを離れた時点で必ず施錠する
- **検索**: パスワードやカード番号など伏せ字の欄は、値を検索対象にしない（検索結果から中身が推測できてしまうのを避けるため）

### ファイル形式の移行

v1（`entries` に平坦な項目が並ぶ形）で作った保管庫は、開いた時点で自動的に v2 へ変換される。
旧「フォルダ」はタグになり、ID はそのまま引き継がれる。上書き前に `vault.pvlt.bak` が作られる。

## 検証済みの動作

`./Tests/run.sh` が実データで確認していること（全 80 項目）:

**暗号**
- 日本語・絵文字を含むパスワードの往復が完全一致する
- ファイル内にパスワード・カード番号・TOTP シークレットの平文が現れない
- 間違ったマスターパスワードを拒否する
- 暗号文の 1 ビット改ざんを検知する
- ヘッダの反復回数を切り下げるダウングレード攻撃を検知する
- 同じ内容を保存しても毎回違う暗号文になる（nonce の再利用がない）
- マスターパスワード変更後、古い鍵では開けなくなる

**ワンタイムパスワード**
- RFC 6238 Appendix B の公式テストベクタ 18 件（SHA1 / SHA256 / SHA512 × 6 時刻）すべてに一致
- `otpauth://` URI から発行元・アカウント・桁数・周期を読み取れる
- 30 秒ごとにコードが切り替わり、枠内では変わらない

**Watchtower**
- 使い回しを関係する全アイテムで検出し、相手の名前を示す
- 弱いパスワード・1 年以上前のパスワード・http:// のサイトを検出
- 問題のない保管庫では指摘ゼロ、ゴミ箱の中は監査対象外

**同期**
- 両端末が同じセッション鍵と同じ確認コードにたどり着く
- **中間者攻撃を再現した場合、両端末の確認コードが必ず食い違う**
- 同期のたびに使い捨ての鍵を作るので、過去の通信を後から解読できない
- 送信データにパスワード・カード番号・タイトルの平文が現れない
- 改ざんされた通信、鍵の違う相手からの通信は復号に失敗する
- TCP が途中で切れても、まとめて届いても、フレームを正しく組み直せる
- 異常に大きな長さ指定を送りつけられても、メモリを確保しに行かない
- 競合は更新時刻の新しい方が勝ち、どちら側から同期しても同じ結果になる
- 完全削除した項目が相手から復活しない（墓標）。ただし削除より後の編集は復活する
- 何度同期を繰り返しても項目が増殖しない

**その他**
- v1 保管庫からの移行で、タイトル・パスワード・ユーザー名・フォルダ・ID が保たれる
- 生成パスワードの出現分布に偏りがない（剰余バイアスなし）
- 伏せ字の欄の値が検索に引っかからない

### 実機（シミュレータ）での確認

iPhone 17 Pro / iOS 26.5 のシミュレータで、実際に画面を操作して次を確認した:

- 保管庫の作成 → 項目の追加 → 保存 → 再起動 → 施錠 → 解錠 → 項目が残っている
- パスワード生成（20 文字・126 ビット）から入力欄への適用
- TOTP の入力欄でコードが即座にプレビューされる
- 表示された TOTP コードが、**Python の独立実装で計算した値と一致**した
- サイドバーの件数表示、空カテゴリの非表示、Watchtower の緑シールド（指摘ゼロ）

同期については、シミュレータ 2 台（iPhone 17 Pro / 17 Pro Max）を実際に操作して確認した:

- 一方を「待つ」、他方を「探す」にして Bonjour で相手を発見できる
- 両画面に**同一の確認コード**が表示される
- 承認後、双方が相手の項目を取り込み、2 台とも同じ内容になる
- **マスターパスワードが違う 2 台でも同期できる**（片方 `TestVault-…`、他方 `SecondDevice-…` で検証）
- TOTP シークレットを含む項目も欠落なく転送される

### Mac ↔ iPhone 間の通信

macOS 版の画面を自動操作する手段がないため、代わりに `Tools/SyncPeer` を使って確認した。
これはアプリと同じ `SyncCrypto` / `SyncFraming` / `SyncMerge` を使う相手役で、Mac 側で動く。

```bash
swiftc -O -o /tmp/syncpeer Tools/SyncPeer/main.swift \
  PassVault/Core/{SyncCrypto,SyncMerge,VaultItem,ItemField,ItemCategory}.swift
/tmp/syncpeer wait   # iPhone 側で「相手を探す」を選ぶ
/tmp/syncpeer find   # iPhone 側で「この端末で待つ」を選ぶ
```

これで確認できたこと:

- シミュレータが **Mac 側で告知された Bonjour サービスを発見**できる
- 接続・鍵交換が成立し、**Mac の標準出力と iPhone の画面に同じ確認コード**が出る（`421 253`）
- 双方の承認後、iPhone の 2 件が Mac 側へ、Mac 側の 1 件が iPhone へ渡り、両者 3 件になる
- ワンタイムパスワードを持つ項目も欠落なく渡る
- 相手が途中で消えた場合、`Connection reset by peer` として画面に出て「やり直す」に戻れる

**未確認**: macOS 版アプリの同期画面を人が操作したときの挙動。通信路とプロトコルは
上記で確認済みで、画面の見た目は下記の `Tools/ViewShots` で確認したが、
実際にボタンを押して同期が始まるところまでは追えていない。

### macOS 版の画面の見た目

Mac の画面収録の許可が下りていない環境では、動いているアプリの画面を撮ることができない
（`screencapture` も Apple Event 経由の操作も拒否される）。そこで `Tools/ViewShots` を使う。

```bash
swiftc -o /tmp/viewshots Tools/ViewShots/ViewShots.swift PassVault/Core/*.swift PassVault/Views/*.swift
/tmp/viewshots /出力先ディレクトリ
```

自分のプロセスで画面外にウィンドウを作り、その中身を自分で取り出すので、
他人のウィンドウを撮るわけではなく許可も要らない。ライト／ダークの両方を書き出す。
**保管庫には一切書き込まない**（見本はビューへ直接渡し、実行の前後でファイルが
変化していないことも確かめている）。

これで実際に見つかった不具合:

- macOS の `Form` は `TextField` の第 1 引数を欄の左のラベルとして描く。
  入力例をそこに渡していたため、タイトル欄には例文の「GitHub」が値と並んで居座り、
  ワンタイムパスワード欄には `otpauth://totp/...` という長い説明文がラベルとして
  表示されていた。iOS では欄内の薄い文字になるので気づけない類の崩れ。
  `prompt:` に移して `.labelsHidden()` を付けて解決。

#### 撮れる画面と撮れない画面

| 画面 | 結果 |
|---|---|
| 設定 / パスワード生成 / 項目の編集 | **撮れる**（`Form` ベース。中身 82〜85%） |
| 項目の詳細 / 一覧 / サイドバー / Watchtower / 同期 | **撮れない** |

撮れないものは、行の背景や区切り線、アイコンだけが描かれて**文字が一切出ない**。
`layer.render(in:)` / `cacheDisplay` / `ImageRenderer` / PDF 経由の 4 通りを試し、
待ち時間を延ばす、`NavigationStack` で包む、といった手も加えたが届かなかった。
`List` と `ScrollView` の中身は、実際の画面に出るまで描かれないのだと考えられる。

出力には「中身 N%」を添えている。これは**目安であって判定ではない**。中央にアイコンと
数行だけの画面は正しく描けていても数 % にしかならず、逆に行の背景だけが描かれた
文字のない画像も数 % になる。数値だけを見て「撮れた」と判断してはいけない
（実際に一度それで誤った）。

**したがって、macOS 版の中核である 3 カラム（詳細・一覧・サイドバー）と Watchtower は
まだ誰も目で見ていない。** 見るには、システム設定 → プライバシーとセキュリティ →
画面収録 で許可を与えるのが確実な道筋になる。

## 同期のしくみ

同じネットワーク上の 2 台を直接つなぐ。クラウドも自分のサーバーも介さない。

```
待つ側                                    探す側
  │  Bonjour で _passvault._tcp を告知      │
  │ ←──────── 見つけて接続 ──────────────── │
  │                                         │
  │ ──── 使い捨ての公開鍵（X25519）────→    │
  │ ←─── 使い捨ての公開鍵（X25519）─────    │
  │                                         │
  │   両者が同じ共有秘密にたどり着く         │
  │   → 6 桁の確認コードを両画面に表示       │
  │                                         │
  │   利用者が目視で一致を確認し、両方で承認  │
  │                                         │
  │ ←── 暗号化した保管庫の中身を送り合う ──→ │
  │        それぞれ自分の側で統合            │
```

**なぜ確認コードを見比べる必要があるのか**: 鍵交換だけでは、同じネットワークにいる第三者が
両者との間でそれぞれ別の鍵交換を行う「中間者攻撃」を防げない。通信自体は成立してしまう。
確認コードは 2 つの公開鍵から導出しているので、割り込まれると 2 台の画面に違う数字が出る。
利用者がそれを見比べることが、唯一の検知手段になっている。

**競合の解決**: 項目ごとに `updatedAt` の新しい方を採用する。どちらの端末から同期しても
同じ結果になり、何度繰り返しても増殖しない。

**完全削除の扱い**: 消した事実を「墓標」として日時つきで残す。これがないと、片方で消した
項目がもう片方から復活してしまう。墓標は 180 日で自動的に掃除される。

**マスターパスワードは送られない**。両端末で違うパスワードを使っていても同期できる。
受け取った中身は、それぞれの端末が自分の鍵で暗号化し直して保存する。

## アプリアイコン

`PassVault/Resources/Assets.xcassets/AppIcon.appiconset/` に置いてある。
青のグラデーションに白い南京錠。図案は外部ツールではなく
`Tools/IconMaker/main.swift` の CoreGraphics コードで描いていて、走らせ直せば全サイズが再生成される。

```bash
swiftc -O -o /tmp/iconmaker Tools/IconMaker/main.swift
/tmp/iconmaker PassVault/Resources/Assets.xcassets/AppIcon.appiconset padlock
```

第 2 引数を `shield` / `vault` にすると別案（盾＋鍵穴 / 金庫扉）も描ける。
`preview` を渡すと 3 案を 512px と 48px で書き出して見比べられる。

小さいサイズでの見え方が図案選びの決め手になる。金庫扉案は名前とよく合うが、
48px でスポークが潰れて丸い塊にしか見えなくなるため採用しなかった。

macOS 用は角丸と余白を自前で描いている（macOS はアイコンをマスクしないため）。
iOS 用は正方形のまま出して OS 側のマスクに任せている。

## Touch ID / Face ID を有効にするには

**署名なし（ad-hoc 署名）のビルドでは動かない。** これは実測で確認済み:

| 試したこと | 結果 |
|---|---|
| 生体認証つき + 新しいキーチェーン | `errSecMissingEntitlement` (-34018) |
| 生体認証なし + 新しいキーチェーン | `errSecMissingEntitlement` (-34018) |
| 生体認証つき + 旧キーチェーン | `errSecMissingEntitlement` (-34018) |
| 生体認証なし + 旧キーチェーン | 成功 |
| `keychain-access-groups` などの権限を ad-hoc 署名で付与 | 起動時に OS が強制終了（SIGKILL） |

つまり権限を自前で付けて回避することはできず、本物の署名 ID が要る。手順:

1. Xcode → Settings → Accounts → ＋ → Apple ID でサインイン（**無料の Apple ID で構わない**）
2. プロジェクトを開き、PassVault ターゲット → Signing & Capabilities タブ
3. 「Automatically manage signing」にチェック
4. Team に自分の名前（Personal Team）を選ぶ
5. ビルドし直す

有効にできていない状態で設定画面のトグルを押すと、この手順を促すメッセージが出る。
マスターパスワードでの解錠には影響しない。

## バックアップ

`vault.pvlt` をコピーしておけばよい。中身は暗号化されているのでクラウドに置いても平文は漏れない。
ただし**マスターパスワードを忘れたら復元手段はない**。設計上そうなっている。

上書き前に `vault.pvlt.bak` を 1 世代残しているが、これは書き込み中のクラッシュ対策であって
世代バックアップではない。

## 未対応 / 今後

- **iPhone 実機での実行**: シミュレータでは動作確認済み。実機に入れるには署名が必要（下記の Touch ID と同じ手順）
- **QR コードの読み取り**: いまは `otpauth://` の文字列を手で貼り付ける必要がある
- **漏洩チェック**: 1Password は Have I Been Pwned に問い合わせて漏洩済みパスワードを警告する。同じことをするなら k-匿名性を使った通信の設計が要る（今は通信ゼロ）
- **自動入力**: macOS / iOS の Credential Provider 拡張
- **自動同期**: いまは毎回手で「待つ／探す」を選ぶ必要がある。信頼済みの端末を覚えておいて
  自動でつなぐようにもできるが、そうすると確認コードによる目視確認を省くことになるので、
  端末どうしの長期的な鍵を保存する仕組みが別に要る
- **iCloud 経由の同期**: 有料の Apple Developer Program（年 99 ドル）が必要。
  無料の Personal Team では iCloud の Capability が使えない

## 注意

自作のパスワード管理ツールは、仕組みを理解するには最高の題材だが、
長年使うメインの金庫としては監査済みの既存ツール（Bitwarden, KeePassXC, 1Password など）のほうが安全。
実装そのものより、鍵の扱いや運用の細部で事故が起きやすい。
