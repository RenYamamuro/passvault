# PassVault（web 版）

ブラウザで動くパスワード管理。**単一の HTML ファイル**をローカルに置いて開く。
通信は一切しない。保管庫は暗号化されたファイルとして自分で持つ。

## 使い方

```
Web/PassVault.html をブラウザで開く
```

初回は「保管庫をつくる」でマスターパスワードを決め、保存先のファイルを指定する。
2 回目以降は「前回の保管庫を開く」を押すだけ（前回開いたファイルを覚えている）。
別のファイルを開くときは「既にある保管庫を開く」から選ぶ。

**保管庫のファイル（`.pvlt`）はダブルクリックしても開かない。** 暗号化されたデータで、
関連付けられたアプリがないため。開くときは必ず `PassVault.html` から選ぶ。

`Web/check-vault.py` を使えば、復号せずにファイルが壊れていないかを確かめられる。
マスターパスワードは要らず、中身も読まない。

```bash
python3 Web/check-vault.py ~/path/to/vault.pvlt
```

## 開発

ソースは分かれていて、`build.py` が 1 つの HTML にまとめる。

```bash
python3 Web/build.py          # Web/PassVault.html を生成
```

| ファイル | 中身 |
|---|---|
| `core.js` | 保管庫の暗号（ファイル形式・鍵導出）、種別のひな型、検索 |
| `crypto-extras.js` | TOTP、パスワード生成、強度推定 |
| `audit.js` | Watchtower、同期のマージ |
| `icons.js` | アイコン（SF Symbols に寄せた線画）と、種別ごとの色 |
| `app.js` | 状態、入口の画面、サイドバー、一覧、自動施錠 |
| `detail.js` | 詳細表示、編集・生成・設定の各ダイアログ |
| `style.css` | 骨組み（配置・寸法・状態）。テーマ変数を使って書いてある |
| `theme-*.css` | 見た目のテーマ。`style.css` に重ねる。単独では使えない |

**`PassVault.html` は生成物なので直接編集しない。**

`build.py` はまとめたあと `node --check` で構文を検める。
壊れたバンドルは画面が真っ白になるだけでブラウザで開くまで気づけず、実際に 2 回やらかしたため。

`file://` ではブラウザが ES モジュールの読み込みを拒否するため、まとめる必要がある。
開発中はローカルにサーバを立てれば分割したまま動かせる。

```bash
python3 Web/serve.py
# http://localhost:8770/index.html  … 分割したままのアプリ
# http://localhost:8770/tests.html  … 検証（157 項目）
#
# serve.py はキャッシュを無効にして配る。素の http.server だと
# ブラウザが古い .js を握ったまま離さず、直したものが直って見えない。
# この作業中だけで 3 回踏んで、そのたびに判断を誤った。
```

## ホーム画面に追加して使う（iPhone / iPad）

```bash
python3 Web/build.py --site
```

`Web/site/` に一式が出る。本体（`index.html`）に加えて manifest、service worker、
アイコンが入る。**HTTPS で配信しないと動かない**（service worker の条件）。

- 保管庫はファイルではなく**この端末の中**（IndexedDB）に置かれる
- 一度開けば電波が無くても動く（service worker が本体を持っている）
- 設定に「この画面の版」が出る。配信元から配っている場合、
  中身が入れ替わっていないかを確かめる手がかりはこれしかない

**単一 HTML を Files アプリから file:// で開く形では動かない。**
iOS Safari は file:// で保存領域を使わせないため、保管庫を置く場所がなくなる。

### 配信

```bash
./Web/deploy.sh
```

`gh-pages` の枝を毎回入れ替えて押し込む。生成物なので `main` には入れない。
送る前に `.pvlt` が紛れていないかを検め、見つかれば中止する。

届いたかどうかは、設定の「この画面の版」を見れば分かる。

### 配信元を信頼することになる

ローカルのファイルとして開く形は、この一点のために選んでいた。
どこかに置いて配ると、**開くたびにそこから届いた JavaScript が
マスターパスワードを受け取る**。置き場所を押さえられたら、
暗号の強さは何の役にも立たない。

減らし方はあるが、無くせはしない。

- ホーム画面に追加すると service worker が本体を抱えるので、
  以後は棚から動く。差し替えは版が上がったときにだけ届く
- 設定の「この画面の版」を見れば、入れ替わったかどうかは分かる
- 置き場所は自分だけが書き込める状態に保つ（二要素認証を必ず有効にする）

## 見た目

骨組み（`style.css`）とテーマ（`theme-*.css`）を分けてある。
`build.py` の `THEME` を書き換えれば切り替わる。

### 構造

**面はひとつ。** 一覧と詳細は「切り替わる画面」であって、並ぶ列ではない。

以前は 3 列（サイドバー / 一覧 / 詳細）だった。既存のパスワード管理ツールに
倣ったものだが、**数十件の保管庫には過剰**で、実際サイドバーはほとんどの行が
「1」の、空の器の集まりになっていた。

いまの造りはこう。

- **検索が主役。** 上の帯でいちばん広い場所を占める。
  種別名・タグ・タイトル・ユーザー名・メモを拾う（伏せ字の中身は拾わない）
- **区分の札は 4 つまで。** すべて / お気に入り / 点検 / ゴミ箱。
  検索で言い表せる種別とタグは札にしない
  （試しに全部出したら 16 個並び、縦の散らかりを横に移しただけになった）
- **一覧から直接コピーできる。** 9 割の用は「探す→写す」で済むので、
  そのために詳細を開かせる理由がない
- 種別とタグへは、詳細画面の種別名とタグ札から入る

### キーボード

| 操作 | |
|---|---|
| 文字を打つ | どこを触っていても検索へ入る |
| `↑` `↓` | 一覧を辿る |
| `Enter` | 開く |
| `⌘C` | 選んでいる項目のパスワードを、開かずに写す |
| `Esc` | 詳細なら一覧へ。一覧なら検索を消す |

### 組みの決めごと

- **余白は 4 の倍数で刻む。** 目が拾える律動を作るため
- **選択は塗りつぶさない。** 地を薄く染めて文字を強める。
  ベタ塗りにすると、種別の色も警告の色も同時に死ぬ
- **影はほとんど使わない。** 境界線と地の明度差で階層を作る
- **色は状態を示すときだけ使う。** 装飾では使わない
- **純白と純黒を避ける。** 目に刺さるうえ、階層も作りにくい

行の右にあるコピーなどの道具は、触れるまで薄くしてある。
並んだ丸が主役に見えると中身が読みにくい。
ただし `hover` を持たない端末では最初から見えている（指で触る前提のため）。

### テーマ

| テーマ | 性格 |
|---|---|
| **`theme-macos.css`（採用中）** | 骨組みそのまま。半透明の帯、システムのアクセント色への追随、種別ごとの色 |
| `theme-tool.css` | 彩度を捨てて情報密度を上げる。種別は色ではなく**アイコンの形**で見分ける |
| `theme-1password.css` | 余白と丸みを多めにとり、種別の色を前に出す |

アイコンは絵文字をやめて単色の線画にした。絵文字は環境ごとに絵柄が変わり、
フルカラーで主張が強く、大きさも揃わない。線画なら文字色に追従する。

半透明を使うが、**本物の vibrancy は再現できない**。
macOS のそれは背後のウィンドウの色を拾って混ぜるが、ブラウザからは背後を覗けないため。

狭い画面には**別の造りを持たない**。面がひとつなので、そのまま縮む。
帯の詰めと、指で触る大きさだけを変えている。

## ファイル形式

**Swift 版（`PassVault/`）とバイト単位で互換。** 同じ保管庫ファイルをどちらでも開ける。

```
┌─ 平文ヘッダ (44 バイト) ────────────┬─ AES-256-GCM ────────────┐
│ "PVLT" │ version │ kdf │ 反復回数 │ salt │ nonce │ 暗号文 │ 認証タグ │
└────────────────────────────────────┴──────────────────────────┘
        └── これ全体を GCM の追加認証データにする ──┘
```

- **鍵導出**: PBKDF2-HMAC-SHA512、32 バイトの salt。マスターパスワードは保存しない
- **反復回数**: 新しい保管庫は 1,200,000 回。Web Crypto の PBKDF2 は Swift 版より
  4 倍ほど速いので、同じ体感の重さにするために増やしてある。
  反復回数はファイルに記録されるので、400,000 回で作られた古い保管庫もそのまま開ける
- **暗号化**: AES-256-GCM。1 ビットでも書き換わっていれば復号が失敗する
- **ヘッダ改ざん対策**: 反復回数と salt を追加認証データに含めてある。
  これがないと「反復回数を 1 に書き換えて総当たりを楽にする」攻撃が通ってしまう
- **日時**: ミリ秒を落として書く。Swift の `JSONDecoder` の iso8601 が小数秒を
  受け付けないため、これを守らないと Swift 版から読めなくなる

## ネイティブ版との違い

web にしたことで**弱くなった点**。ここは曖昧にしない。

| | ネイティブ版 | web 版 |
|---|---|---|
| コードの出所 | インストールした実体が動き続ける | 開くたびにファイルを読む。ファイルが差し替われば何でもできる |
| XSS | 関係なし | スクリプトが 1 つ通れば復号済みの中身が全部読める |
| 鍵の保管 | Keychain（生体認証で保護可） | 保管しない（毎回パスワード入力） |
| 生体認証 | Touch ID で鍵を出せる | **なし**。WebAuthn は認証であって鍵導出ではない |
| メモリ | 鍵をゼロ埋めできる | JavaScript では消せない |
| クリップボード | 履歴アプリに「保存するな」と伝えられる | 伝える手段がない。30 秒後に上書きするだけ |
| ローカル同期 | Bonjour + TCP で実装済み | **できない**。ブラウザから TCP を張れない |

クラウド同期のフォルダに置く場合、ファイルが外から変わっていれば
**取り込む／上書きする／何もしない**の 3 択を出す。「取り込む」を選べば、
そちらの変更と手元の変更を突き合わせて 1 つにまとめる。
気づかないまま相手の変更を消すことはない。

保存しようとした時点だけでなく、**開いている間も 15 秒ごとにファイルの更新時刻を見に行く**。
別のタブから戻ってきたときも一度見る。相手の変更が降りてきていれば知らせて、
取り込むかどうかを訊く。訊かずに差し替えることはしない（編集中の内容が消えるため）。

ローカルに置いて開く形にしているのは、この表の 1 行目を潰すため。
ホスティングして「どこからでもアクセス」にすると、配信元を完全に信頼することになる。

## できること

ログイン / セキュアメモ / クレジットカード / ID・個人情報 / APIキー / Wi-Fi / ライセンスの
7 種別、ワンタイムパスワード（TOTP）、Watchtower、パスワード生成、
お気に入り・タグ・全文検索、パスワード履歴、ゴミ箱、カスタム欄、自動施錠。

前回開いた保管庫のファイルは覚えておく（File System Access API のハンドルを IndexedDB に
保存する）。保存されるのは「このファイルを触る権利」だけで、保管庫の中身も鍵も含まない。
次に開くときブラウザが許可を訊き直す。

### ファイルに書けない環境（iOS の Safari など）

`showSaveFilePicker` が無いブラウザでは、保管庫を**この端末の中**（IndexedDB）に
暗号化したまま置く。置くのは暗号文とファイル名と保存時刻だけで、鍵は入らない。
取り出せてもマスターパスワードが無ければ読めない。

入口に「この端末の保管庫を開く（保存日時）」が出るので、そこから解錠する。

**ブラウザの保存領域は消えることがある。** iOS はしばらく使わないサイトの領域を
消すことがあるので、`navigator.storage.persist()` で消さないよう申し出るが、
断られることもある。ホーム画面に追加してあると通りやすい。控えの書き出しは必須。

バックアップの書き出しは `vault-backup-2026-07-30.pvlt` のように日付が入る。
本体と同じ名前にすると、どちらが使っている保管庫か区別できなくなるため。

**自動の同期はない。** 代わりに**取り込み（マージ）**がある。
設定の「別の保管庫を取り込む…」から相手のファイルを選ぶと、項目ごとに更新時刻の
新しい方を残して 1 つにまとめる。どちら側から取り込んでも同じ結果になり、
何度繰り返しても増殖しない。

**相手のファイルが別のマスターパスワードで作られていても取り込める。**
そのファイルのパスワードを訊いて開き、**取り込んだ結果は手元の鍵で書き直す**ので、
以後も自分のパスワードで開ける。

取り込む前に、追加される項目・上書きされる項目の一覧と件数を見せて確認を取る。

端末の中に保管庫を置いている場合は、設定に「**同期用に書き出す**」が出る。
控えと違って日付を付けず保管庫と同じ名前で書き出すので、
クラウド上の同じファイルに上書きして戻せる。

## 検証済みの動作

`http://localhost:8770/tests.html` が確認していること（全 157 項目）。

**暗号（Swift 版との互換を含む）**
- Swift 版が作った保管庫を復号でき、絵文字・日本語を含むパスワードが完全一致する
- web 版が書いた保管庫を Swift 版が読める（別途 Swift 側で確認済み）
- 間違ったパスワード、1 ビットの改ざん、反復回数の切り下げをすべて拒否する
- 同じ内容を保存しても毎回違う暗号文になる（nonce の再利用がない）
- ファイル内にパスワードの平文が現れない

**ワンタイムパスワード**
- RFC 6238 Appendix B の公式テストベクタ 18 件（SHA1 / SHA256 / SHA512 × 6 時刻）に一致
- `otpauth://` URI から発行元・アカウント・桁数・周期を読み取れる

**取り込み（マージ）**
- 別のマスターパスワードで作られた保管庫も、そのパスワードを訊いて取り込める
- **取り込んだ結果は手元の鍵で書かれる**（相手の鍵で書くと次に自分で開けなくなる）
- 競合した項目は更新時刻の新しい方が残り、どちら側から取り込んでも同じ結果になる
- 同じものを 2 回取り込んでも増えない
- 相手側で完全に削除された項目は、こちらからも消える（墓標）

**画面の部品**
- `aria-*` / `data-*` がプロパティではなく**属性**として設定される
  （`Object.assign` で作っていた頃は黙って無視され、読み上げに何も伝わらなかった）
- ダイアログを閉じると自動施錠の停止が必ず解ける
  （後始末を `<dialog>` の `close` イベント任せにしていたところ、
  そのイベントが飛んでこない環境があり、**一度開くと自動施錠が永久に止まっていた**）
- 確認ダイアログは閉じたら「いいえ」、確定したら「はい」を返す
- 文字を訊くダイアログは空のままでは確定せず、前後の空白を落とす

**マスターパスワードの変更**
- 新しい鍵で書けたときだけ差し替わる
- 変更後は新しいパスワードで開け、**古いパスワードでは開けなくなる**
- 書き込みに失敗したら鍵とヘッダを元に戻す
  （書けないまま鍵だけ変えると、画面の鍵とファイルの鍵が食い違って以後なにも保存できない）

**施錠しても変更を捨てない**
- 保存できていない変更があるまま自動施錠するとき、まず保存を試み、
  それでも駄目なら**暗号化したまま抱えて**から施錠する
  （以前は中身を無条件に捨てていたので、書き込みに失敗したまま放置すると変更が消えた）
- 抱えた中身は暗号文で、平文が残らない。施錠の意味は保たれる
- 次に**同じパスワードで解錠できたときだけ**取り戻すか訊く。
  別の保管庫やパスワード変更後は開けないので、取り違えは起きない

**端末の中への保存（ファイルに書けない環境）**
- ファイルに書けない環境でも保存が成功し、未保存の印が消える
  （以前はここで「抱えておく」と返すだけで、実際はメモリ上にしか無く、
  **タブを閉じた時点で消えていた**）
- 端末に置くのは暗号文とファイル名と保存時刻だけで、鍵は入らない
- 別のパスワードでは端末の中身も開けない
- 端末にも書けなかった場合は成功と偽らず、理由を返す

**別の端末の変更を取りに行く**
- ファイルが新しくなっていたら知らせる。変わっていなければ何もしない
- ダイアログを開いている間と施錠中は割り込まない
- **読んだだけでは下敷きの時刻を動かさない**
  （動かしていたため、取り込みを途中で取り消すと相手の変更を見なかったことにして、
  次の保存で黙って踏み潰していた）

**検索**
- 種別名でも絞れる（「ログイン」「カード」と打てば効く）。
  ここが効くので、画面に種別ごとの入れ物を並べずに済んでいる
- 伏せ字の中身（パスワード・カード番号）は検索対象にしない

**保存の安全性**
- 書き込みの失敗を例外ではなく戻り値で返し、必ず画面に出す
  （投げっぱなしにすると「画面には反映されているがファイルには書かれていない」状態が
  何も表示されないまま残ってしまう。パスワード管理として最悪の失敗の仕方）
- ファイルが外から書き換えられていたら競合として止め、**1 バイトも書かない**
- 上書きを選んだ場合だけ書き込む
- 保存先を持てない環境（Safari など）では未保存として扱い、画面に示す
- マスターパスワードの変更は、書き込めなかったら鍵ごと元に戻す
  （書けないまま鍵だけ変えると、画面の鍵とファイルの鍵が食い違う）

**その他**
- 生成パスワードの出現分布に偏りがない（剰余バイアスなし）
- 伏せ字の欄の値が検索に引っかからない
- Watchtower が使い回し・脆弱・古い・http:// を検出し、ゴミ箱は対象外にする
- マージはどちら側から取り込んでも同じ結果になり、繰り返しても増殖しない
- 古い形式（v1 / v2）の保管庫を読める

**画面**（ブラウザを操作して確認）
- 3 カラム構成、ライト／ダークの両方
- 項目の詳細（伏せ字、強度バー、TOTP の残り時間の輪、履歴、Watchtower の指摘）
- 保管庫の作成、編集、パスワード生成、設定、新しい項目の選択、
  Watchtower の一覧、ゴミ箱、競合の 3 択、検索 0 件
- 狭い画面（390px）でのサイドバー・一覧・詳細の行き来
- **マスターパスワードの変更**（間違った現パスワード・短すぎる新パスワード・
  入力の不一致をそれぞれ拒否し、正しく変えると古いパスワードで開けなくなる）
- **競合の 3 択から「取り込む」まで**（外から書き換わった状況を作り、
  止まること・1 バイトも書かないこと・取り込むと双方の項目が残ることを確認）
- まとめた `PassVault.html` が単体で動く（暗号往復・UI 描画・TOTP すべて）

各画面には機械的な検査もかけている（`undefined` / `NaN` / `[object` の混入、
横方向のはみ出し）。ただし**数値で測れるのはそこまで**で、
「×印が意味的に不適切」のような崩れは目で見るまで分からなかった。

## 注意

自作のパスワード管理ツールは、仕組みを理解するには最高の題材だが、
長年使うメインの金庫としては監査済みの既存ツール（Bitwarden, KeePassXC, 1Password など）
のほうが安全。**web 版はネイティブ版よりさらに前提が弱い**（上の表のとおり）。
実装そのものより、鍵の扱いや運用の細部で事故が起きやすい。

マスターパスワードを忘れたら復元手段はない。設計上そうなっている。
